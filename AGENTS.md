# AGENTS.md

## Purpose

This repository contains `OpenCode Workspace Manager`, a Windows WPF application that creates, provisions, manages, and launches local OpenCode workspaces from official Ubuntu LTS containers.

This file captures the working guidance for contributors and coding agents so the repository remains understandable without external conversation history.

## Product Direction

Priorities:

- ship a usable Windows executable
- keep the code and manifests readable
- prefer canonical YAML over opaque runtime state
- prefer official sources over custom images
- validate real behavior before packaging or release work

Avoid:

- clever abstractions that hide control flow
- reflection-heavy plugin designs
- service locators
- modifying unrelated user terminal profiles or shell configuration

## User Experience Model

Main UI mental model:

- the app is a workspace launcher and manager first, not a Docker console
- primary user intent is `Open Workspace`
- the app should decide when start, update, restart, attach, and validation are required
- Docker lifecycle details belong in diagnostics and troubleshooting, not in the main dashboard

Primary user-facing workspace states:

- `Deluje`
- `Ustavljen`
- `Posodobitev na voljo`
- `Napaka`

Status guidance:

- use a native WPF colored status indicator, not emoji or font-dependent glyphs
- the colored dot is the primary signal, text is secondary
- keep the same status component consistent across cards, details, and future summaries or filters

Interaction guidance:

- single click selects a workspace and updates details
- double click opens the workspace using the primary action flow
- Enter on the selected workspace also opens it
- keep the right-side `Open Workspace` action for discoverability, but make list interaction the fastest path

## Architecture Summary

Projects:

- `src/OpenCode.Workspace.Core/`: portable models, catalog loading, generation, diagnostics, orchestration
- `src/OpenCode.Workspace.Manager/`: WPF shell and Windows-specific behavior

Key principle:

- `workspace.yaml` is canonical and portable
- generated files are implementation details
- containers are disposable
- mounted folders hold durable state

## Generated Artifacts

Generated runtime artifacts include:

- `compose.yaml`
- `.env`
- `mounts/config/provision.sh`
- `mounts/config/starship.toml`
- `mounts/config/opencode-shell-init.sh`
- `mounts/config/applied-state.yaml`

Every generated file must contain a header explaining:

- this file is generated
- source inputs that produced it
- whether user edits are preserved

Durable changes belong in `workspace.yaml` or catalog manifests, not generated files.

Applied state rules:

- successful workspace update or provisioning must persist an applied-state record
- restart or stop/start alone must not mark a workspace as needing update
- update-required detection should compare current desired/generated state to the persisted applied state
- applied-state should reflect the resolved workspace definition and generated runtime plan, not just timestamps

## Terminal Ownership Rules

OpenCode Stuff may:

- create and manage its own Windows Terminal fragment profile definitions
- create and manage its own generated Starship configuration
- manage clearly marked OpenCode Stuff sections in the workspace user's shell configuration

OpenCode Stuff must not:

- modify unrelated Windows Terminal profiles
- modify unrelated shell configuration outside clearly marked managed sections

Terminal defaults:

- prompt: `starship` recommended
- preferred Nerd Font: `JetBrainsMono Nerd Font`
- additional supported Nerd Fonts: `CaskaydiaCove Nerd Font`, `FiraCode Nerd Font`
- optional utilities: `zoxide`, `fzf`

Important font note:

- the user-facing preference name may differ from the actual Windows Terminal font face name
- validate the actual configured profile face and the actual registered Windows font family before accepting terminal screenshots
- do not use a terminal screenshot in release materials if glyphs render as diamonds, boxes, or replacement characters

## Docker and Provisioning Guidance

The project provisions from official Ubuntu LTS containers instead of maintaining custom development images.

Provisioning rules:

- install from official Ubuntu repositories where possible
- install OpenCode from the official npm package
- keep provisioning steps readable in generated scripts
- use LF line endings for scripts that run inside Linux containers
- stream Docker stdout/stderr to the UI during start and prepare operations
- create and repair required OpenCode user directories before first launch

OpenCode first-run directories:

- ensure `/home/opencode/.local/share/opencode/log`
- ensure `/home/opencode/.config/opencode`
- ensure `/home/opencode/.cache/opencode`
- repair ownership back to `opencode:opencode` when old workspaces were previously initialized by root
- continue launching OpenCode as `opencode`, not root

Start/prepare success rules:

- do not report success before post-command validation passes
- validate with `docker compose ps` and expected container checks
- treat stderr as diagnostic output, not automatic failure
- treat exit code and validation checks as the source of truth

## Attach Behavior

Attach flow:

1. ensure the workspace is running
2. launch Windows Terminal with the OpenCode Stuff managed profile
3. run the attach command inside the workspace container

Current attach command contract:

```bash
/opt/opencode-workspace/config/opencode-workspace-shell.sh
```

Notes:

- interactive terminal handoff is partly manual by nature
- automated validation should focus on readiness and session state, not perfect terminal UX replay
- attach must run as the `opencode` Linux user, not root
- the durable workspace shell loop recreates the `opencode` screen session and restarts `opencode -s` if OpenCode exits
- the Windows Terminal command should stay boring and inspectable; prefer a generated wrapper script over deeply nested `wt.exe` quoting
- log the exact `wt.exe` command, profile name, configured font, profile file path, and effective attach user during troubleshooting
- before attach, repair missing or non-writable OpenCode user directories and log `[attach] Initializing OpenCode user directories.` when repair was needed

## Removal Behavior

Removal choices must stay explicit:

- remove from list only
- remove Docker resources
- remove Docker resources and delete local files

Destructive removal rules:

- do not delete files when the user selected remove-from-list only
- before deleting workspace files, stop the workspace and run `docker compose down --remove-orphans`
- before Windows deletes the workspace folder, run a Docker-based permission normalization step for mounted Linux-created files
- if deletion still fails, keep registration intact, report actionable failed paths, and offer repair-and-retry instead of silently partially deleting

## Windows Prerequisites

OpenCode Stuff requires:

- hardware virtualization enabled in BIOS or UEFI
- Docker Desktop for Windows
- WSL2 backend enabled for Docker Desktop
- Windows Terminal
- .NET 10 Desktop Runtime

Keep the README brief and user-facing, and put detailed setup guidance in `docs/windows-prerequisites.md`.

Health checks should explain clearly when any of these are missing:

- virtualization disabled or WSL2 unavailable
- Docker Desktop not installed
- Docker Engine not reachable
- Windows Terminal not installed
- .NET Desktop Runtime missing

## Agent Safety Rule: Do Not Kill Host Terminal

Automated agents must not kill Windows Terminal, the current host shell, the running app under test, or broad host processes during smoke tests.

Terminal attach behavior should be validated by generated configuration and command strings.

Real interactive attach and focus behavior is a manual validation step.

## Testing Strategy

Two integration test categories are required:

### Portable / Cross-Platform

These must validate the canonical model and generation pipeline without depending on:

- Docker Desktop
- Windows Terminal
- WPF
- Windows-only APIs

Focus areas:

- YAML load/save
- catalog loading and validation
- template expansion
- dependency resolution
- compose generation
- `.env` generation
- provisioning script generation
- generated headers
- archive import state tracking
- workspace persistence rules

### Windows Integration

These validate Windows-specific behavior such as:

- Docker Desktop detection
- Windows Terminal detection
- Nerd Font detection
- terminal profile generation
- localization loading
- app bootstrap and WPF startup
- Docker orchestration helpers
- attach command generation

If prerequisites are missing, tests must skip with explicit reasons rather than fail ambiguously.

## Build Guidance

WPF and Windows-specific artifacts must be built on the Windows host .NET SDK.

Example from WSL:

```bash
cmd.exe /c "cd /d C:\Users\miha.pirnat\source\repos\opencode-stuff-init && dotnet build OpenCode.Workspace.Manager.slnx"
```

Do not attempt to build WPF inside Linux containers.

## Release Readiness

Before MSIX packaging or release work, prioritize validation of:

- create workspace
- generate compose artifacts
- provision workspace
- start workspace
- stop workspace
- attach workspace
- restore OpenCode session
- display meaningful diagnostics on failure

Packaging should package a validated product, not become the validation milestone.
